# Oracle hosting fit for Docket: Arm wheels, CPU and memory

Date: 2026-10-16   Task: NOTASK-32   Status: research, nothing was run on a host
Supports: `docs/adr/0018-host-on-1-gb-on-oracle-cloud-and-waive-the-no-card-rule.md` (the engineer kept the 1 GB shape as the target and chose to record these findings without superseding the ADR).
V = verified (file:line or URL), I = inferred. Every I figure must be measured on the host before it is relied on.

Summary: the 1 GB AMD shape has 1/8 of a CPU and about 920 MB is needed at the OCR peak against about 900 MB usable, so it runs only on swap and reads will be slow. The Arm A1 shape (about 2 OCPU, 12 GB) has aarch64 wheels for every binary dependency in `uv.lock`. The Makefile defaults `DEPLOY_PLATFORM` to `linux/amd64`.


## 1 Arm fit (V: uv.lock wheel lists, parsed locally; every wheel URL in the lock)
All binary deps have Linux aarch64 wheels for cp314 (or abi3) at the pinned versions:
onnxruntime 1.30.0 cp314 manylinux_2_28_aarch64 (no musllinux, no sdist); opencv-python-headless 4.14.0.94 cp37-abi3 manylinux2014/2_28 aarch64; pyclipper 1.4.0 cp314 manylinux_2_28 aarch64 only (no musllinux; Debian is glibc so fine); shapely 2.1.2 cp314 manylinux2014 + musllinux; numpy 2.5.3 cp314 manylinux_2_28 + musllinux; pillow 12.3.0 cp314 manylinux_2_28; pydantic-core 2.46.5 cp314 manylinux2014 + musllinux; asyncpg 0.31.0 cp314 manylinux2014 + musllinux; argon2-cffi-bindings 26.1.0 cp310-abi3 manylinux_2_28 + musllinux; cffi 2.1.1 cp314 manylinux2014; greenlet 3.5.6 cp314 manylinux_2_28 + musllinux; uvloop 0.23.0 cp314 manylinux2014 + musllinux; httptools 0.8.0 cp314 manylinux2014 + musllinux; watchfiles 1.3.0 cp310-abi3 manylinux2014 + musllinux; rapidocr 3.9.2 pure python (none-any wheel); pdf2image 1.17.0 pure python; pyyaml, markupsafe, sqlalchemy, protobuf (abi3) also have aarch64 wheels.
Dockerfile: python:3.14-slim-bookworm, apt poppler-utils only (Dockerfile). poppler-utils 22.12.0-2+deb12u3 exists for arm64 (V: https://packages.debian.org/bookworm/poppler-utils). python:3.14-slim-bookworm, postgres:16, nginxinc/nginx-unprivileged:1.28-alpine, node:24-alpine, ghcr.io/astral-sh/uv:0.11.30 arm64 manifests: NOT checked (I: all are multi-arch official images).
What would break: nothing in dependencies. Makefile:198 DEPLOY_PLATFORM defaults to linux/amd64, so deploy-build would ship wrong-arch images; set DEPLOY_PLATFORM=linux/arm64 (needs buildx + QEMU on the laptop; no compiles because all are wheels, but slow emulated build, I). Not measured: ONNX/RapidOCR accuracy and speed on aarch64 (OCR output could differ in float rounding, I). Caddy installed via apt in bootstrap (Makefile:238) is available for arm64 on Ubuntu (I).

## 2 CPU fit
V: ONNX is pinned to 1 intra and 1 inter thread (app/gateway/rapidocr_engine.py:40-41), so the 1.4 s/page benchmark (docs/research/ocr-benchmark.md rows: 1.42 and 1.47 s) is effectively single-core; multi-core laptop is not the multiplier. V: the 30-page tuned run took 44.8 to 53.2 s (about 1.5 to 1.8 s/page) with the child recycled after every page, so model load is included (NOTASK-17-memory.md). V: runtime run, 34 docs incl. four 25 MP PNGs, --cpus=1, 97.29 s (about 2.9 s/doc).
V: Oracle: E2.1.Micro is "1/8th of an OCPU with the ability to use additional CPU resources" (Always Free doc). The shape page lists 1 OCPU and EPYC 7551/7742/7J13 cores, so burst to a full core is allowed; the sustained baseline figure is not documented in what I fetched (I: 12.5%).
I: EPYC core at burst is similar to the laptop core, 1.5 to 3 s/page. Throttled to 12.5% sustained: 8x, so 12 to 25 s/page, worse while Postgres, gunicorn, Docker and Argon2 (64 MiB, t=3, config.py) compete. Worst case with credit/steal exhaustion 30 to 60 s. All under READ_TIMEOUT_SECONDS 120 (config.py:49) per page, so single pages likely do not time out, but with little margin on large uploads; a queue of 34 docs would take 7 to 15 min. Time-out is per read (process.py:78 poll(read_timeout)), queue wait is not counted. This estimate is not measured.
A1 (V: Ampere Altra Q80-30, 3.0 GHz, 1 OCPU = 1 core): full cores, no throttle. I: 1.5 to 3 s/page, close to the laptop; with 2 OCPU the worker, Postgres and nginx do not starve each other.

## 3 Memory on one 1 GB machine
V: API 449.5 MB peak (cgroup memory.peak, 34 docs, 512 MB limit), compose caps api at 640m with no memory-swap set (docker-compose.prod.yml, so swap up to another 640m is allowed per V: Docker docs). V: Postgres 16 defaults shared_buffers 128 MB, work_mem 4 MB, maintenance_work_mem 64 MB (https://www.postgresql.org/docs/16/runtime-config-resource.html). Pool is 5 + 10 overflow (config.py) and each backend costs several MB (I).
I typical figures (no source fetched): Ubuntu base + sshd + systemd 100 to 150 MB; dockerd + containerd 80 to 150 MB; Caddy 20 to 40 MB; nginx alpine 5 to 15 MB; Postgres total 150 to 250 MB with 128 MB shared_buffers touched; kernel/page cache reserved on a 1 GB VM leaves about 900 MB usable.
Sum at peak: 450 + 200 + 120 + 110 + 30 + 10 about 920 MB of about 900 usable. VERDICT: does not fit without swap; with swap it runs but peaks swap to a 1/8 OCPU disk (slow, network block volume). Bootstrap already creates a 2 GB /swapfile (Makefile:240-245) but the 449 MB peak is during OCR, the exact moment swap hurts most.
Lowest-risk config on E2.1.Micro (I): keep 2 GB swap, vm.swappiness 60 to 100 is fine, set API_MEM_LIMIT=512m, Postgres -c shared_buffers=64MB -c max_connections=20, DB_POOL_SIZE=2, keep ENGINE_RECYCLE_AFTER=1, WEB_CONCURRENCY=1, drop Caddy for nginx only if TLS is handled elsewhere (not recommended), docker logging limits. Demo traffic only, one OCR at a time.

## 4 Recommendation
B) Arm A1 Flex (2 OCPU, 12 GB; V Oracle doc) is the better fit: wheels exist, memory fit is trivial (could even run 4 GB, 1 OCPU), no CPU throttle, no swap. Caveats: V capacity "might be limited" for A1 in a region; V idle reclamation if 95th pct CPU, network and memory all below 20% over 7 days (a demo might trigger it; Oracle states it applies to compute instances); arm64 images untested; ADR-0018 line 45 already flags this open question. Fallback A) E2.1.Micro with the config above, expect 10 to 25 s/page.

Pass bar: no OOM kill (dmesg), zero failed documents, longest read below 60 s, swap in/out near zero on A1.
